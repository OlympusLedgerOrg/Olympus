# ── Soundness UB in glib (Linux only, transitive Tauri) ──────────────
#
# RUSTSEC-2024-0429 — glib <0.20.0: unsoundness in `Iterator` /
# `DoubleEndedIterator` impls for `VariantStrIter::impl_get`.
# `&p` (immutable) was passed where the C variadic out-argument expected
# `&mut p`; recent rustc optimisations discard those writes, so the
# subsequent `CStr::from_ptr(p)` dereferences NULL → crash / UB.
#
# Patched in glib >= 0.20.0. Olympus is on glib 0.18.5, transitive via:
#   tauri 2.11.5 → muda/tao/webkit2gtk/wry → gtk 0.18.2 → glib 0.18.5
# tauri 2.11.x is pinned to the gtk-rs 0.18 family; we cannot bump glib
# in isolation without ripping out the whole gtk binding stack.
#
# Runtime exposure: reachable only through `GVariant` string-iterator
# code paths inside the webview chrome (drag-drop payloads, file-chooser
# dialogs, system menu items). The first-party Axum/sqlx/ZK paths are
# unaffected. Linux-only — Windows and macOS Tauri builds don't load
# this glib code.
#
# This is the single advisory that is more than "unmaintained" — it is
# exploitable soundness UB. Listed separately so a future reviewer
# doesn't lump it back into the gtk-rs cluster.
#
# MITIGATION ALREADY APPLIED — DO NOT MISREAD AS "WE SHIP THE BUG".
# The fix from gtk-rs/gtk-rs-core#1343 (`let mut p` + `&mut p,` in
# `VariantStrIter::impl_get`) is backported in-tree at
# `crates/glib-0.18.5-patched/src/variant_iter.rs` and wired via
# `[patch.crates-io] glib = { path = "..." }` in the workspace
# `Cargo.toml`. cargo-audit matches advisories by name+version only and
# cannot see the [patch] override, so it still flags `glib 0.18.5` —
# hence this ignore entry. Retire BOTH the ignore AND the vendored
# crate when either (a) webkit2gtk-rs moves to glib ≥ 0.20, or (b)
# upstream publishes glib 0.18.6 with the fix. See
# `crates/glib-0.18.5-patched/PROVENANCE.md` for the retire procedure.
RUSTSEC-2024-0429

#
# ── crypto-bigint 0.5.5 — the stated fix is not installable ────────────────
#
# RUSTSEC-2026-0387 — subtraction, zero counting, division and Montgomery
# multiplication in crypto-bigint could branch on secret data; `UintRef`
# equality and `BoxedMontyForm::invert` likewise. Patched in >= 0.7.6.
#
# WARNING: THIS ONE IS A REAL EXPOSURE, NOT A DORMANT ENTRY.
# crates/babyjubjub-permissive/src/ct.rs uses crypto-bigint's
# `modular::constant_mod::Residue` for exactly the secret-scalar Baby Jubjub
# arithmetic (256 fixed double/add/select rounds) that the crate is built
# around, and `Residue` multiplication is Montgomery multiplication. The
# constant-time property ct.rs relies on is what the advisory puts in
# question, so this needs a deliberate decision rather than a bump:
#   * the patched line cannot be installed. 0.7.5, 0.7.6 and 0.7.7 are ALL
#     yanked on crates.io ("selected package was yanked by the author"), and
#     no 0.6.x or 0.8.x release exists, so there is no non-yanked version to
#     move to;
#   * `elliptic-curve 0.13.8` (via ecdsa 0.16.9 <- k256 0.13.4 <-
#     ethers-core 2.0.14 <- ark-circom 0.6.0) pins `crypto-bigint = "^0.5.5"`
#     independently, and 0.5.5 is the version keyed here.
# Second path, lower risk: the k256/ECDSA route verifies public ethers-core
# data; no long-lived secret scalar goes through it.
#
# Unblock (either):
#   (a) a non-yanked crypto-bigint >= 0.7.6 — then move ct.rs onto it and let
#       elliptic-curve 0.14 / k256 0.14 catch up for the ethers-core edge; or
#   (b) vendor 0.5.5 with pull/1365's branch removal the way glib and
#       ppv-lite86 are already vendored, and retire it the same way.
# Track as a security follow-up; do not let this entry sit unchallenged.
RUSTSEC-2026-0387

#
# RUSTSEC-2026-0459 / CVE-2026-119375 — SQLite before 3.54.0 can return
# uninitialized page-cache memory when a database is opened together with a
# sibling `-wal` whose page size differs. Fixed by libsqlite3-sys 0.39.0
# (bundled SQLite 3.54.0).
#
# What was fixed: pg-embed-local's lockfile now uses sqlx 0.9.1 +
# libsqlite3-sys 0.39.0 (sqlx-sqlite 0.9.0 capped the requirement at
# "<0.38.0"; 0.9.1 allows ">=0.30.1, <0.41.0"), so that lockfile passes.
#
# Why the workspace lockfile still resolves 0.30.1: libsqlite3-sys declares
# `links = "sqlite3"`, so a graph may contain exactly one copy, and
# rusqlite 0.32.1 — pulled by tor-dirmgr 0.31.0 <- arti-client 0.31.0 behind
# the optional `federation` feature — requires `^0.30.1`. Cargo resolves
# optional dependencies into the lockfile, so that requirement pins the shared
# package for the whole workspace even though the feature is off:
#     $ cargo update -p libsqlite3-sys@0.30.1 --precise 0.39.0
#     error: failed to select a version for the requirement
#            `libsqlite3-sys = "^0.30.1"` ... required by package `rusqlite`
# arti-client 0.31.0 is the newest 0.31.x, and rusqlite has no newer
# compatible release, so no lockfile edit resolves this.
#
# WARNING: blast radius is NOT zero. The resolved 0.30.1 is the copy
# sqlx-sqlite builds (bundled SQLite 3.46.x) in the default desktop build, so
# it is what ships. Exploitation needs a local db + `-wal` pair written by a
# less trusted party and then opened by the process; Olympus opens its own
# application database, but any path that opens a user-supplied SQLite file
# would expose it. Verify that assumption before shipping such a path.
#
# Unblock (either):
#   (a) drop or narrow the `federation` feature so rusqlite leaves the resolve
#       graph — then sqlx can take 0.39.x (its trusted-setup ceremony has not
#       been run, so the feature is not usable in production today); or
#   (b) an Arti release whose tor-dirmgr accepts rusqlite >= 0.41.
RUSTSEC-2026-0459
