## Headline result

Across the post-V5 delta:
**0 Critical · 0 High · 1 Medium · 2 Low · 4 Informational.**

Nothing found this round is remotely exploitable, and nothing found is a **soundness** break —
no bug in this report causes an invalid bundle, proof, credential, or checkpoint to be accepted.
The single Medium is the inverse: a **completeness** failure on the court-evidence surface. The
two offline redaction verifiers — the artifacts whose whole purpose is out-of-band, no-trust-in-
the-issuer verification — reject every genuine bundle the shipping producer emits for the
`pdf-object`, `pdf-xref-stream` and `ooxml-part` formats. The drift is invisible to CI because
the cross-language conformance vectors are hand-built to match the *verifier*, not generated by
the *producer*.

Every hard invariant pinned in `CLAUDE.md` was re-checked against the delta and **holds**:
ADR-0005 structured leaf prefix and the shard/parser-provenance binding (now verified
byte-identical across four independent implementations), JCS/RFC-8785 canonicalization,
insert-only ledger with the typed `WriteOnceViolation` guard and no delete path anywhere,
fail-closed SBT scope mapping, the unconditional shard `authorize_write` gate, quorum domain
separation (`OLY:SBT:QUORUM:V2` and its three disjoint siblings), all four ceremony-integrity
checks, the `CircomProvingKey` prove seal, `acquire_write_lock` serialization, ADR-0022
`LAZY_DEPTH=72` / `CANOPY_RECOMPUTE_CAP=1024`, and the H-2 `treeSize=0` invariant on
`/zk/verify`. Two circuit edits in the delta (`LessThanBounded` normalisation, `ledgerKeyHash`
binding) are strict **strengthenings** and are documented as such below.

**V5 residue: both remaining V5 Lows are FIXED.** See [V5 residue](#v5-residue) for the code
cites.

### Methodology this round

V6 keeps V5's recon→hunt shape and adds an adversarial **verification** stage between hunting
and reporting:

- **Recon (3 agents):** trust-boundary map of the delta; exhaustive route/parser/IPC input
  inventory with per-route auth, size and rate limits; and an invariant-enforcement map that
  located every enforcement site for the twelve pinned `CLAUDE.md` invariants and flagged which
  were touched by the delta.
- **Hunt (7 parallel agents), one per surface:** signature-envelope (ADR-0035),
  request-envelope (ADR-0036), redaction/textrun, anchoring, federation, crypto-core parity
  (Rust ↔ JS ↔ Python), and invariant regression. Each was required to produce a concrete
  exploit path — attacker, controlled input, code path, gain — not a theoretical concern.
- **Adversarial verification:** every candidate went to **three independent skeptics** with
  different lenses (does the code actually say this / is it actually reachable / is it novel and
  in-scope). A candidate survived only if fewer than half the skeptics refuted it. **21
  candidates were raised; 14 were refuted and killed.** The refutations are the most valuable
  output of the round and are folded into
  [What held under attack](#what-held-under-attack).
- **Lead re-verification:** every survivor re-read against source by the audit lead before
  write-up, including a first-principles adjudication of the three-way convergence on the
  verifier-drift finding (see [Adjudication](#adjudication-of-the-three-way-convergence)).
- **Read-only engagement.** No `cargo build`, `cargo test`, or dynamic execution. Findings are
  static reading plus `git diff`/`git log`, corroborated where possible by replaying the exact
  byte-emission algorithms out of band. See [Coverage note](#coverage-note).

### A1-01 — Medium — Offline redaction verifiers reject every real PDF/OOXML bundle the producer emits

**Component:** `verifiers/rust/src/redaction.rs`, `verifiers/javascript/test_redaction.js`
**Introduced by:** `81cd315f` (#1325, "Harden redaction artifact verification"), interacting with
`1b049980` (#1311, ADR-0034)

Commit #1325 added artifact-replay hardening to both offline verifiers —
`validate_canonical_pdf_container`, `validate_canonical_ooxml_central_directory`,
`validate_redacted_bytes` — so that a recipient re-derives every segment span from the artifact
instead of trusting bundle-supplied offsets. The intent is correct and the checks are, in
isolation, sound. But every byte-level constant in them was modelled on the hand-rolled
fixtures in `crates/olympus-crypto/examples/gen_redaction_vectors.rs`, **not** on the shipping
producers. The two disagree on at least six independent fields, any one of which is a hard
reject. `text-line` is the only format where producer and verifier agree end-to-end.

**Confirmed divergences** (each independently fatal; all re-read against source by the lead):

| # | Field | Producer emits | Verifier requires |
|---|---|---|---|
| 1 | PDF header | `%PDF-1.7\n` — `zk/pdf_objects.rs:601`, `zk/segment/pdf_xref.rs:629` | `%PDF-1.4\n` — `redaction.rs:432`, `test_redaction.js:325` |
| 2 | xref free-list | standalone `0 1\n0000000000 65535 f \n` subsection, then contiguous in-use runs — `pdf_objects.rs:644` | object 0 merged into the first contiguous run (`0 N`) — `redaction.rs:461-467` |
| 3 | xref generation | real `{generation:05}` — `pdf_objects.rs:656` | hardcoded `00000` — `redaction.rs:486` |
| 4 | trailer | real `/Root` via `find_root_ref`, or `/Root` omitted — `pdf_objects.rs:662-665` | hardcoded `/Root 1 0 R` — `redaction.rs:492` |
| 5 | `pdf-object` destroyed form | `N G obj\nnull\nendobj` (ADR-0034) — `pdf_objects.rs:611` | all-NUL/whitespace body (the superseded in-place fill) — `redaction.rs:885` |
| 6 | `ooxml-part` zip metadata | zip 8.6.0 `SimpleFileOptions::default().compression_method(Stored).last_modified_time(default_for_write()).unix_permissions(0o644)` → local/central version 10, `mdate` 33, non-zero external attributes — `zk/segment/ooxml.rs:113-119` | version 20/20, `mdate` 0, external attributes 0 — `redaction.rs:564-570, 635-646` |

A seventh, narrower divergence: for `pdf-xref-stream` the producer's committed span is
`[start_k, start_{k+1})`, which **includes** the `\n` separator after `endobj`
(`pdf_xref.rs:690-697`), while the verifier's `pdf_object_span` ends exactly at the end of
`endobj` (`redaction.rs:343`) — an unconditional off-by-one on every object, reported as
`"bundle offset/length != artifact-derived span"`.

Divergence #5 deserves separate emphasis because it inverts a security property rather than
merely mismatching a constant. ADR-0034 §2 mandates the fixed-width `null` token precisely so
that *the artifact never discloses the hidden object's byte length*, and lists the
width-preserving NUL fill under **Rejected** alternatives. The verifier still enforces the
rejected form. The adjacent `pdf-xref-stream` arm (`redaction.rs:892`) correctly requires
`b"null"` — so the same function holds two contradictory destroyed-form rules, which is direct
in-tree evidence of drift rather than of intent. `docs/adr/ADR-0030` §3 also still carries the
stale sentence "`pdf-object` NUL-fills the object body in place", contradicting ADR-0034 §2.

**Why CI is green.** Both verifiers load only `verifiers/test_vectors/redaction_vectors.json`
(`redaction.rs:1137` `include_str!`, `test_redaction.js:62`), generated by
`gen_redaction_vectors.rs`. That generator **hand-builds** its containers:
`build_traditional_pdf` opens `let mut buf = b"%PDF-1.4\n".to_vec();` (line 182) with a merged-run
xref loop that is a line-for-line twin of the verifier's `expected` reconstruction, and its
`pdf-object` redacted body is `let obj4_body = b"\x00\x00\x00\x00\x00\x00\x00";` (line 448) — seven
NUL bytes, i.e. the pre-ADR-0034 fill, whose length equals the hidden body's length. It lives in
`olympus-crypto`, which cannot depend on `src-tauri`, so it *structurally cannot* call the real
producer. No test anywhere feeds `apply_redaction_with_spans` output to `verify_bundle`.
ADR-0034 §"Crypto invariance" explicitly recorded that the vectors "do not regenerate" and that
the change involved "no ... verifier leg changes" — true when written at #1311, silently
invalidated by #1325 six days later.

**Exploit path / who is harmed.** There is no attacker; the harmed party is the honest
recipient. (1) The user ingests any PDF or `.docx/.xlsx/.pptx`. (2) The user calls `POST
/redaction/redact`; `api/redaction/redact.rs:63,142` returns `redacted_base64` plus the signed
V3 bundle. (3) The recipient — opposing counsel, a court, an auditor — replays those bytes
through `olympus_verifier::redaction::verify_bundle` or the JS equivalent and receives
`RejectReason("non-canonical pdf container")` / `"redacted pdf bytes not destroyed"` /
`"non-canonical ooxml zip entry"` — the *exact* strings the verifier emits for a genuinely
tampered artifact. An authentic Olympus disclosure is indistinguishable from a forged one.

**Impact.** ADR-0030 names the offline verifier as "the security boundary for post-Groth16
redaction", and `docs/court-evidence.md:130` sells this replay as evidentiary claim 5 ("the
redaction was correct"). That control is inoperative for every format a real document uses. It
is **fail-closed** — no forged or downgraded bundle is accepted, so this is not a forgery
primitive — but the second-order risk is significant: because the conformance suite is green,
the tempting "fix" is to change the *producer* to satisfy the verifier, which would reinstate
exactly the byte-length oracle ADR-0034 was written to close. **The verifier is the side that is
wrong.** A further consequence is that the whole #1325 replay-hardening layer has never been
exercised against real producer output, so a genuine soundness gap inside it would be equally
invisible.

Rated **Medium** rather than Low: the court-evidence/offline-verifier surface is explicitly
in-scope for this engagement, the failure covers essentially every real document, and it makes
a documented product guarantee false. Rated **not High** because it is fail-closed, requires no
attacker, and the redaction verifier currently ships as a library — `verifiers/rust/src/bin/verify.rs`
exposes only a Groth16 `verify` subcommand and the JS logic lives inside `test_redaction.js`, so
a recipient must drive it as a library today.

**Code citation:**
```rust
// producer — src-tauri/src/zk/pdf_objects.rs:601, 611, 644
out.extend_from_slice(b"%PDF-1.7\n");
let null_obj = format!("{} {} obj\nnull\nendobj", obj.obj_id, obj.generation);
out.extend_from_slice(b"0 1\n0000000000 65535 f \n");

// verifier — verifiers/rust/src/redaction.rs:432, 486, 492, 885

expected.extend_from_slice(format!("{off:010} 00000 n \n").as_bytes());

if inner.iter().all(|&b| b == 0 || PDF_WS.contains(&b)) { Ok(()) } else { Err(RejectReason("redacted pdf bytes not destroyed")) }
```

**Fix** — make the producer the source of truth, then close the loop with a test:

1. **The missing gate (do this first).** Add a round-trip test per format that runs
   `zk::segment::apply_redaction_with_spans` and feeds `(artifact, bundle)` straight into
   `olympus_verifier::redaction::verify_bundle`. `verifiers/rust` is excluded from the cargo
   workspace, so this needs an explicit CI job. Everything below is a symptom of this test not
   existing.
2. **Regenerate the vectors from real producer output** instead of `build_traditional_pdf` /
   `build_stored_zip` — or relocate the canonical-container writers into `olympus-crypto` so
   producer and generator share one implementation.
3. **Until (1)/(2) land, align the constants:** header → `%PDF-1.7\n`; accept the standalone
   `0 1` free-list subsection; accept the artifact's real `/Root` and real generation numbers;
   make `validate_redacted_bytes("pdf-object")` require exactly the ADR-0034 `null` token (and
   **stop** accepting arbitrary-length NUL/whitespace fill, which is the size oracle); reconcile
   the `pdf-xref-stream` span boundary on one side or the other; pin the OOXML writer's
   version / mtime / external-attribute fields explicitly rather than relying on
   `unix_permissions`, and drop the platform-dependent `system` default — today central
   `version_made_by` differs between Windows and Linux builds, which is a build-determinism bug
   in its own right.
4. **Fix the ADR drift:** correct `ADR-0030` §3's "`pdf-object` NUL-fills the object body in
   place" to match ADR-0034 §2.

### L-01 — Low — Unbounded mutual recursion in the PDF structural-object guard

**Component:** `src-tauri/src/zk/segment.rs:279` (`pdf_type_name::skip_group`)
**Introduced by:** `e9105ab3` (#1306) — new in this delta; absent at `ed782e44`.

`skip_group` is mutually recursive across the dict/array boundary: inside a dictionary a `[`
recurses into `skip_group(.., array=true)`, and inside an array a `<<` recurses into
`skip_group(.., array=false)`. Same-kind nesting is handled by the iterative `depth` counter, but
alternating `[<<[<<[<<…` nesting adds a stack frame roughly every 1.5 input bytes with **no depth
cap and no cumulative budget**. It is the only recursive parser in the segmenter tree
(`pdf_xref.rs`, `ooxml.rs`, `text.rs`, `pdf_objects.rs` were all checked and contain no self- or
mutually-recursive helper). Note the codebase already knows this pattern — `pdf_describe.rs:33`
declares `const MAX_PAGE_TREE_DEPTH: usize = 64` and `anchoring/ots_format.rs` uses `MAX_DEPTH =
64` — the guard was simply omitted here.

**Exploit path.** Attacker = the author of a document the user is asked to ingest (in-scope
untrusted-ingest surface). (1) Craft a PDF where a plausibly-redactable object has a body of the
form `<< /A ` followed by tens of KB of the repeating 3-byte sequence `[<<`; arming every object
is cheap. (2) The user ingests via `POST /ingest/files` — extraction (`pdf_objects.rs:382-470`) is
purely iterative and never calls the guard, so the file commits normally and the UI lists all
objects. (3) The user selects that object and calls `POST /redaction/redact`;
`api/redaction/redact.rs:63-65` runs `apply_redaction_with_spans` **inline on the Tokio worker**
(no `spawn_blocking` on this path) → `rebuild_redacted` → `pdf_objects.rs:594-597`
`pdf_structural_object_type(body)` on the uploaded bytes → the outer key walk at `segment.rs:416`
dispatches `skip_value` → `skip_group`. Recursion measures at ~0.67 frames/byte; a Tokio
worker's 2 MiB default stack overflows in the tens of thousands of frames, so a ~30–60 KB object
body suffices. (4) Rust converts a guard-page hit into `abort()` — no unwinding, no HTTP 500, no
message in the UI, process gone. Reachable through both PDF segmenters (`pdf_objects.rs:800`,
`pdf_xref.rs:739`).

**Impact.** Availability only — no confidentiality or integrity effect, no ledger corruption
(committed rows are durable and Postgres is a separate process). Recoverable by restarting the
app. No existing bound helps: `MAX_OBJECTS`/`MAX_REDACTION_SEGMENTS` (2²⁰) caps segment *count*,
`MAX_INFLATE` caps decompression volume, and the 128 MB `DefaultBodyLimit` does not constrain a
60 KB body — none of them bound parser recursion.

Rated **Low** rather than Medium (the panel corrected the hunter's Medium 3/3, and I agree):
unlike V5's A1-02, which fired during ingest parsing itself, this requires a *second* deliberate
user action — selecting the armed object and invoking redaction.

**Code citation:**
```rust
// src-tauri/src/zk/segment.rs:279 — no depth parameter, no budget
fn skip_group(b: &[u8], mut i: usize, array: bool) -> usize {
    i += if array { 1 } else { 2 };
    let mut depth = 1usize;
    while i < b.len() && depth > 0 {
        let c = b[i];
        if c == b'<' && b.get(i + 1) == Some(&b'<') {
            if array { i = skip_group(b, i, false); }   // nested dict inside an array
            else { depth += 1; i += 2; }
        } else if c == b'[' {
            if array { depth += 1; i += 1; }
            else { i = skip_group(b, i, true); }        // nested array inside a dict
        }
```

**Fix.** Convert `skip_group` to an explicit iterative walk over a `Vec<bool>` stack of group
kinds, or thread a `depth: usize` and bail at a PDF-realistic cap (64, matching
`MAX_PAGE_TREE_DEPTH`). **Bail direction matters:** returning `None` from `pdf_type_name`
classifies the object as *non-structural* and would therefore **allow** the redaction — the cap
must produce an explicit "unparseable, refuse" outcome, not a silent `None`. Add a regression
test with `b"<< /A " + b"[<<".repeat(100_000)` asserting a bounded result rather than a crash.

### L-02 — Low — Non-2xx anchor responses bypass the 10 MiB response cap

**Component:** `src-tauri/src/anchoring/rfc3161.rs:194`, `src-tauri/src/anchoring/ots.rs:147`
**Note on scope:** this code is unchanged since the V5 baseline (`git diff ed782e44..HEAD` on both
files is empty). It is a gap the #1184 OTS-2 hardening PR missed, surfaced this round rather
than introduced by the delta. Reported because the control it defeats is explicitly declared
global.

`anchoring/http_limits.rs` exists specifically to stop an adversarial anchoring backend from
streaming an unbounded body into memory — its header calls this red-team **OTS-2 (HIGH,
CONFIRMED)** and sets `MAX_ANCHOR_RESPONSE_BYTES = 10 MiB`, enforced by a chunked
`bytes_stream()` reader. Two call sites read the body *before* the cap applies:
`rfc3161::submit_with_nonce` and `ots::try_upgrade` both call `resp.text().await` on the
non-success branch, which fully buffers with no size limit. `rekor::submit` (`rekor.rs:159-161`)
and `ots::submit` (`ots.rs:60-67`) get the ordering right — capped read first, status check
after — which makes the two error paths an oversight rather than a design decision.

**Exploit path.** Attacker = the configured anchor backend itself: a compromised RFC 3161 TSA
(`OLYMPUS_ANCHOR_RFC3161_URL`) or OTS calendar (`OLYMPUS_ANCHOR_OTS_CALENDARS`) — parties the
anchoring design explicitly treats as untrusted. The anchor cron ticks (default 3600 s, floored
at 60 s; OTS upgrade cron 6 h, floored at 300 s), POSTs the checkpoint digest, and the backend
answers with any non-2xx status — including a **3xx**, since the V5 L-02 fix set
`redirect::Policy::none()` and every redirect now lands on this exact branch — then streams an
arbitrarily long body. `resp.text()` buffers the whole stream and additionally runs a lossy UTF-8
decode, so invalid-UTF-8 input inflates ~3× into the decoded `String` while the raw `Bytes` is
still alive. Only 512 chars are ever retained.

**Impact.** Transient memory amplification (~4× the streamed body) against an opt-in feature on
an operator-chosen endpoint. Bounded by the client's 30 s total timeout (`state.rs:172`) times
link bandwidth — on 100 Mbps roughly 375 MB streamed / ~1.5 GB peak. Availability only; no
integrity or confidentiality impact and no state loss (the `own_checkpoints` row is committed
before `anchor_all` runs, and `anchor_all` collects per-backend errors and continues). The
hunter's claim that this escalates to a guaranteed process `abort()` and a restart crash-loop is
**not substantiated** and is not asserted here. Anchoring is disabled by default
(`AnchoringConfig::default()` is all-`None`) and reqwest is declared without any decompression
feature, so a hostile backend gets zero amplification and must push every byte. Rated **Low**:
a real ~2-orders-of-magnitude gap versus the 10 MiB the code claims to guarantee, on a declared
remote surface, with a three-line fix.

**Code citation:**
```rust
// src-tauri/src/anchoring/rfc3161.rs:192-201 — cap is only on the success path
let status = resp.status();
if !status.is_success() {
    let detail = resp.text().await.unwrap_or_default();       // ← unbounded
    return Err(AnchorError::Server { status: status.as_u16(), detail: detail.chars().take(512).collect() });
}
let body = super::http_limits::read_response_capped(resp, "RFC 3161 TSA reply").await?;
```

**Fix.** Restructure both functions to match `rekor::submit`: capture `status`, perform the
capped read unconditionally, then branch — so there is exactly one body read per function and no
path can regress. Since only 512 chars are retained, a dedicated small cap (8 KiB) for error
bodies is also fine. Separately, consider clamping `ots::submit`'s stored `receipt_blob` to
`ots_format::MAX_RECEIPT_BYTES` (64 KiB): the submit path currently accepts and persists up to
10 MiB, but `extract_commitment`/`walked_contains_commitment` reject anything over 64 KiB, so an
oversized pending receipt is guaranteed-unupgradable dead weight that the upgrade cron retries
forever.

## Adjudication of the three-way convergence

Three independent hunters (redaction-textrun, crypto-core-parity, invariant-regression)
converged on the verifier-drift claim now reported as **A1-01**. All three shared the same recon
briefing and were each tasked with verifier parity, so correlated false-positive was a live
possibility and the engagement asked the lead to adjudicate directly. I did.

**The decisive question was whether `gen_redaction_vectors.rs` constructs bundles the way the
production producer does, or the way the verifier expects. It is unambiguously the latter.**
`build_traditional_pdf` opens with a literal `b"%PDF-1.4\n"` (line 182) and reimplements the
merged-run xref layout by hand; `build_stored_zip` hand-writes version 20 / mdate 0 / external
attributes 0; the `pdf-object` fixture's redacted body is a literal 7-NUL array (line 448). None
of the shipping producers is called anywhere in that file, and — being in `olympus-crypto`,
which cannot depend on `src-tauri` — none can be. I additionally read both sides of each of the
six divergences directly and reproduced the byte layouts.

**Verdict: confirmed, high confidence.** The three reports are one defect, merged into A1-01.
The reports' *severity* varied (two Medium, one Low) and the skeptic panel split
Medium/Low/Informational across the three; I settled on **Medium** for the reasons stated in the
finding. Two sub-claims from the individual reports were **not** carried over because I could
not sustain them: (a) that the verifiers thereby "bless" a length-leaking NUL-fill artifact — a
pre-#1311 in-place fill preserves the original document's header/xref/trailer and so fails
`validate_canonical_pdf_container` before ever reaching the lenient branch; and (b) that a
recipient hits this today through a shipped CLI — no redaction-bundle CLI exists on either leg.
The OOXML half of divergence #6 is traced from the vendored `zip-8.6.0` source rather than from
an executed `.docx` redaction; the mechanism is unambiguous (and the version and `mdate`
mismatches are each independently fatal), but see the [Coverage note](#coverage-note).

## Informational / hardening (not findings)

- **`pdf-textrun` offline verification is materially weaker than every other format, and must
  be fixed before ADR-0029 Phase B is promoted.** `pdf_textrun_spans`
  (`verifiers/rust/src/redaction.rs:807`, mirrored at `test_redaction.js:603`) derives spans
  only from `(...)` literals followed by `Tj`/`TJ`/`'`/`"`, checks only that the word count
  equals the revealed-segment count, and gives redacted segments a zero-length span at offset 0.
  It calls **no** `assert_spans_tile`, **no** container validation, and **no** `%%EOF` /
  trailing-byte check — the only arm in `artifact_spans` with none of these. Consequently
  everything outside the revealed word spans is uncommitted: bytes appended after the last
  committed word (an entire PDF incremental update redefining `/Contents`) leave every signed
  offset, every leaf, the fold, `table_hash`, the signature and the nullifier intact. Equal-length
  in-place edits to non-word bytes (`Td` coordinates, `Tf` font, `/Encoding /Differences`) are
  likewise unconstrained, and `/ActualText` and hex-string show operands are skipped entirely by
  `show_string_ranges`, so a "redacted" word can survive in a parallel text representation.
  `validate_redacted_bytes`'s `pdf-textrun` arm asserts an always-empty slice is empty, i.e. it
  is vacuous. **Not a finding today** — `textrun-segmenter` is off by default
  (`src-tauri/Cargo.toml:30,54`), `segmenter_for(PdfTextRun)` returns `None` without it
  (`zk/segment.rs:575-576`), `granularity=word` degrades to the object ladder, and `format` is
  inside the Ed25519 signed payload (`redaction.rs:964`) so no other format's bundle can be
  relabelled into this path. No Olympus build can mint a `pdf-textrun` bundle. **Promotion
  checklist:** route the artifact through `validate_canonical_pdf_container` (the producer
  already rebuilds via `rebuild_traditional_with_spans`, so it can satisfy it), tokenize words
  only inside identified content-stream object bodies rather than over raw file bytes, commit
  the enclosing content-stream object and the font/encoding resource, reject non-whitespace
  after `%%EOF`, add a negative vector (append `\n%hidden\n` to the positive bundle and assert
  both legs reject), and decide explicitly whether `/ActualText`, `/Alt`, `ToUnicode` CMaps and
  hex-string operands are in scope for word redaction. Note the committed `pdf-textrun` vector
  artifact is a bare content-stream fragment while the producer emits a full PDF — vector and
  producer disagree on the container shape as well.
- **ADR-0036's signed-admin gate is opt-in, inert by default, and proves cryptographic intent
  rather than identity.** `verify_wire_envelope` verifies Ed25519 against the public key carried
  *inside the envelope* (`signature_envelope.rs:294-296`); neither `operator_id` nor `key_id` is
  resolved against any registry, and none exists (`migrations/0018`'s
  `operators.ed25519_public_key` is read exactly once, by a `COUNT(*)` in `public_stats.rs`).
  This is **not** a defect — the gate is strictly additive, every gated route still runs
  `require_admin_auth` in-handler, `VerifiedSignedRequest` has zero consumers, and ADR-0036 was
  amended in `6060e967` to say exactly this ("verify the cheap Ed25519 leg **in the signature
  envelope**"; "the existing handler still enforces `x-admin-key` or admin-role/admin-scope
  API-key auth"). Four candidate findings built on this were refuted. Three residual hardening
  notes for whoever promotes the slice out of scaffold status: (1) bind `key_id` to
  `operators.ed25519_public_key` before any handler treats `VerifiedSignedRequest::require_scope`
  as an authorization decision — `require_scope` compares a caller-chosen string; (2) the method
  filter (`signed_request.rs:298`) omits `PUT`, so `PUT /federation/peers/{id}/trust` — the only
  `PUT` in the crate — escapes an otherwise-enumerated prefix; add it when the gate gains a trust
  anchor; (3) `reserve_nonce` derives `expires_at` from `Utc::now()` rather than the signed
  `timestamp_utc`, so a future-dated envelope's acceptance window can outlive its replay record —
  use `max(now, timestamp_utc) + W`.
- **ADR-0035 wire-name inconsistency.** `SignatureAlgorithm::wire_name()` and ADR-0035's prose
  spell the PQC algorithm `ml-dsa-65` (the FIPS 204 spelling), while the serde kebab-case
  encoding actually on the wire is `ml-dsa65` / `hybrid-ed25519-ml-dsa65`. `wire_name()` has zero
  callers repo-wide, so nothing emits the wrong string today and the mismatch is fail-closed
  (an unknown variant is a serde parse error → 400). Resolve before an ML-DSA verifier lands:
  either add `#[serde(rename = "ml-dsa-65")]` or delete the unused helper. Relatedly,
  `VerifiedEnvelope.suite` echoes an unauthenticated wire claim next to genuinely-verified
  fields — consider renaming it `claimed_suite` or dropping it.
- **Anchor digests are BLAKE3 but declared SHA-256** in the RFC 3161 `messageImprint`
  AlgorithmIdentifier and the Rekor `hashedrekord` algorithm field. There is no registered
  BLAKE3 OID for RFC 3161 and no `blake3` member of Rekor's algorithm enum, so submitting an
  opaque 32-byte commitment under the only supported 32-byte label is mechanically forced, and
  all documented verification paths (`openssl ts -verify -queryfile/-digest`, `rekor-cli get
  --uuid`) compare imprint *bytes* and are unaffected. A finding claiming this voids the receipts
  was refuted 3/3. What is real is a **documentation error**: `docs/court-evidence.md:129` says
  the TSA "signs `SHA-256(checkpoint)`", contradicting line 128's correct
  `anchor_hash = BLAKE3(OLY:CHECKPOINT_ANCHOR:V1|…)`. Fix that sentence. A second, separate doc
  bug in the same section: line 187's `openssl ts -verify -queryfile <raw 32 bytes>` is the wrong
  flag — `-queryfile` expects a DER `TimeStampReq`; the correct invocation is `-digest <hex>`.
- **`docs/threat-model.md:251` overstates the anchoring response cap**, claiming the 10 MiB limit
  applies to "calendar / TSA / Rekor reads" and citing `anchoring/rfc3161.rs` by name. Per L-02
  that file's non-2xx branch is uncapped. Correct the doc alongside the code fix.
- **`OTS` upgrade `MAX_DEPTH = 64` is counted per *operation*, not per Merkle level**
  (`anchoring/ots_format.rs`). A genuine upgraded receipt (calendar aggregation path plus a
  Bitcoin block Merkle path, each level costing an APPEND/PREPEND plus one or two SHA-256 ops)
  could plausibly exceed 64 ops and be rejected as `DepthExceeded`, in which case every OTS row
  would silently stay `phase=pending` forever (`upgrade_cron::run_once` only emits
  `tracing::debug!` on that branch), quietly voiding the one anchor that requires no trust in any
  private party. This fails closed and is a functional rather than security concern; it could not
  be confirmed without a real calendar receipt. Worth a maintainer check against an actual
  `alice.btc.calendar.opentimestamps.org` upgrade blob.
- **`clients/python/src/olympus_manifest/hashing.py` is an undeclared fourth implementation of
  the ADR-0005 leaf hash and SMT walk.** It is byte-correct today (I diffed all four preimages),
  but it is not wired into the vectors-driven cross-language conformance loop the way the Rust
  and JS verifiers are, and Python is nominally retired per `CLAUDE.md`. Either wire it into the
  vector suite or delete it — an unloved fourth implementation is exactly how the
  verifier-parity-drift class recurs.
- **`verifiers/test_vectors/vectors.json` contains no negative SMT vector.** Every
  `ssmf_existence_proof` / `ssmf_nonexistence_proof` case carries `expected_valid: true`. All the
  fail-closed predicates (empty `shard_id`/`parser_id`/`cpv`/`model_hash`, wrong `value_hash`
  width, `shard_id_matches_key`, 255 siblings, corrupted sibling) *are* enforced and the Rust and
  JS in-code negative suites are symmetric — but the shared vectors do not prove it, so a future
  third implementation could drift silently. Add negative cases to the shared file.
- **`ADR-0030` §3 vs `ADR-0034` §2 contradiction** on the `pdf-object` destroyed form — see
  A1-01 fix step 4. Also `docs/architecture.md:223` still describes the federation equivocation
  seen-set as in-memory; it has been Postgres-backed since `ed782e44`.
- **Duplicated `LAZY_DEPTH`.** `72` is declared independently in `smt/tree.rs:80`,
  `api/smt_stats.rs:30` (used in a query bind) and `examples/smt_read_stress_benchmark.rs:48`,
  plus migration `0044`. They agree today; a divergence would be a migration-class silent
  correctness bug. Export the one const.
- **`api/credentials/crypto.rs:22` is the only fail-open canonicalization site** in the tree —
  `canonicalize_bytes(&raw).unwrap_or(raw)` silently falls back to raw `serde_json` bytes for the
  SBT `commit_id` digest when JCS canonicalization fails (documented rationale: >64 nesting
  depth). `details` is attacker-influenced at issue time. Prefer an explicit error over a
  non-JCS preimage entering a signed digest.
- **Circuit changes in this delta are strengthenings, recorded for the reader's benefit.**
  `LessThanBounded` in `document_existence.circom` and the unified circuit moved from
  `diff.in <== in[1] - in[0] + 2^n; out <== diff.out[n]` to the canonical circomlib form
  `diff.in <== in[0] + 2^n - in[1]; out <== 1 - diff.out[n]`. The old form set `out = 1` when
  `leafIndex == treeSize` — an off-by-one admitting a one-past-the-end index — and was
  unsatisfiable at `treeSize == 2^n`; the new form requires strict `<`. Separately the unified
  circuit replaced free `ledgerPathIndices[256]` with `ledgerKey[32]` plus a public
  `ledgerKeyHash = Poseidon(lo, hi)`, closing a hole where an unconstrained prover chose
  arbitrary SMT path bits. The Rust `ledger_path_indices()` bit order and `pack_le_bytes`
  packing were verified to match the circom `Num2BitsStrict(8)` loop exactly.

## What held under attack

This section is built from what the hunters actually tried and could not break, and from the
14 candidate findings the skeptic panel killed. Negative results are the point.

**Signature and request envelopes (ADR-0035 / ADR-0036).** No unsigned-algorithm or "none"
acceptance — `SignatureAlgorithm` has two variants, serde rejects anything else at the parse
boundary, `validate_shape` requires every descriptor algorithm to be present and rejects
out-of-suite and duplicate components, and `verify()` unconditionally verifies the Ed25519 leg
before anything else. Downgrade against a `HybridRequired` verifier fails: the mode looks the
`MlDsa65` *component* up directly rather than trusting the suite label, and `HybridRequired`
unconditionally returns `UnsupportedAlgorithm(MlDsa65)` — it never silently degrades. The
signed preimage is injective (every variable field `u32`-BE length-prefixed, no delimiter
joining), so the C-3 pipe-injection class does not apply, and `OLY:SIGNATURE-ENVELOPE:V2` is
neither prefix nor suffix of any of the nine other Olympus domain tags. `verify_strict` closes
malleability and torsion. The suspected route-normalization bypass of the gate's raw prefix
match (`//admin/shards`, `/%61dmin/shards`, `/admin/./shards`) is **not real**: no
`NormalizePathLayer` exists anywhere in the stack and Axum's `matchit` matches the same raw
path bytes, so every string that skips the gate also 404s. Envelope↔request binding could not be
loosened: payload must be byte-identical to its own JCS re-canonicalization, `body_hash` is over
the decoded bytes, the *exact verified bytes* are what gets forwarded to the handler, and method
and path are cross-checked against the live request. The JCS canonicalizer that runs pre-auth is
depth-capped at 64, so the classic recursive-descent stack overflow does not fire. Four
candidate findings on this surface were refuted 3/3, 3/3, 3/3 and 2/3.

**Redaction bundle soundness (the half A1-01 does not touch).** I could not construct an
accepted-but-wrong bundle. The segment table is length-prefix framed and injective in
`table_hash`; the Ed25519 payload binds `root_hex / format / N / recipient_id / table_hash`;
`segments.len() == N` is enforced. Segment swap, duplicate id, offset ±1, length −1, overlap,
insertion, truncation, `redacted`-flag flip, format downgrade and recipient replay all break the
signature or a structural check, and the verifiers' own adversarial suites pin exactly these.
Revealed content is pinned by the Pedersen+Poseidon fold, so intra-span substitution is a hash
collision. Canonical-form validators reject `>= r` / `>= l` **without mod-reducing** on both
legs, boundary-tested at `r-1`/`l-1`. The ADR-0034 length-hiding property itself **holds**: for
every shipping format the published redacted `artifact_length` depends only on public data, the
manifest's original `byte_length` is not forwarded, and `label` is forced to `None` for every
non-OOXML format — which matters, because the `text-line` manifest label is literally
`"lines 12-18"` and would otherwise have leaked block geometry.

**Cross-language crypto parity.** The ADR-0005 structured leaf hash is byte-for-byte identical
across **four** implementations (`olympus-crypto`, `verifiers/rust`, `verifiers/javascript`,
`clients/python`) — same prefix bytes, same u32-BE length prefixes, raw un-prefixed 32-byte
`value_hash`, same `0x05` body framing. All three proof verifiers reject empty
`shard_id`/`parser_id`/`cpv`/`model_hash`, a mis-width `value_hash`, and a `shard_id` that does
not hash to the key's 64-bit prefix, and all three call `shard_id_matches_key`. SMT walk
direction, sibling count and sibling width agree. JCS: both Rust and JS NFC-normalize keys *and*
values before sorting, so the classic "JS normalizes, Rust doesn't → two documents collide"
signature-transfer bug does not exist; the known IEEE-754 number-emission divergence is
documented in place as audit M-1, is `skip`-reported rather than silently passed, and is not on
any JS signature-verification path. `DOMAIN_NODE = 2` is consistent across Rust, circom, the
segment fold, the vector generator and both verifiers. Pedersen `OLY:PEDERSEN:H:V1` NUMS
derivation matches across both Rust implementations and both verifiers' hardcoded `H`, which is
re-checked on-curve and in-prime-subgroup. The new parallel `smt_batch` builder produces
byte-identical roots, proofs and prefix roots to the serial builder (arena rebasing verified by
hand: leaf indices stay global, only branch indices are offset).

**Federation.** A re-attack on V5's A1-03 fix failed on every axis: the TOCTOU is genuinely
closed by the single-transaction advisory lock; the dedup key is server-assigned (`peer_id` is
never wire-supplied); the seen-set is Postgres-backed and survives restart; there is no
un-flag path anywhere (`equivocation_detected` is written only by the INSERT and a monotone
`SET … = true`). Envelope field mixing fails — the BJJ signature binds `(root, ts)` and the
proof binds `(root, tree_size)`, with `root` as the shared pin. Weaponised auto-block fails
under normal operation because an honest node's `own_checkpoints` carries
`UNIQUE (ledger_root, tree_size)` over a monotone snapshot. Cross-role signature reuse between
the co-sign oracle and the five sibling BJJ domains requires a BLAKE3 preimage break. Quorum
verification counts a signature only if the signer normalises into the pinned set, is not
already counted, and verifies over a message binding threshold and the canonical sorted signer
set — so a DB-tier threshold downgrade zeroes the count rather than satisfying the quorum. The
Tor listener is a genuinely separate loopback listener and `build_tor_router` omits every
admin/auth/key/write/prove route, with each federation admin handler *additionally* calling
`require_admin` individually. Gossip carries no peer lists and no transitive relay, so there is
nothing to amplify. Four candidate findings on this surface were refuted 3/3.

**Anchoring.** The OTS binary parser resists the obvious sinks: `read_varint` is capped at 8
LEB128 bytes so offsets cannot overflow `usize`; `walk_timestamp`/`scan_for_commitment` are
depth-capped at 64; the `0xff` sibling loop restores only `msg` and never the cursor, so total
work is strictly linear (no exponential blowup); unknown op tags are hard errors rather than
silent skips, so a calendar cannot desync the running `msg`; the deliberately-refused legacy
SHA-1/RIPEMD-160 ops stay refused. RFC 3161 response handling binds correctly: `PKIStatus`,
`eContentType == id-ct-TSTInfo`, `messageImprint.hashedMessage == our hash`, canonical-DER
`NULL` algorithm parameters via `decode_as::<Null>` rather than a tag-only check, and a nonce
re-derived through the *shared* encoder so request and response cannot drift. Rekor receipts are
verified, not merely stored: `verify_entry_matches_hash` runs unconditionally and independently
of SET verification, so a spliced response for another entry is rejected even with SET checking
off, and the SET itself is ECDSA-verified over a JCS canonicalization against an
operator-pinned key, fail-closed in production. There is no fail-open on anchoring failure — a
receipt row exists only on success. `validate_anchor_url` parses with the `url` crate rather
than prefix-matching, rejects userinfo outright, and restricts plaintext `http` to exactly
`localhost`/`127.0.0.1`, so `http://localhost.evil.tld` and `http://attacker@localhost/` both
fail. `federation::checkpoint::anchor_checkpoint` — which would let peer input drive outbound
anchor calls — has **zero** callers at HEAD. Two candidate findings refuted 3/3.

**Invariants and the delta's own hardening.** The insert-only ledger holds: `smt/` is
byte-identical to the baseline, a repo-wide sweep for `DELETE FROM smt_*` / `fn remove` /
`delete_leaf` / `tombstone` returns nothing, the only production `update_batch` caller is
`update_batch_write_once`, and `federation/` cannot reach a leaf write at all. The shard gate is
still unconditional — the new `granularity` multipart field is parsed before it with no early
return reaching ingest. SBT scope mapping, `CircomProvingKey` sealing (still the single
`Groth16::<Bn254, CircomReduction>::prove` call in the workspace, still backed by the
`clippy.toml` `disallowed-methods` ban), the write-lock read-modify-write span with the
cache refresh *inside* the locked section, and the `treeSize=0` invariant (whose call sites
survive the unified circuit's 4→5 public-signal growth because `ledgerKeyHash` was *appended*)
all hold. I independently recomputed the LF-normalised BLAKE3 of both committed vkeys against
their regenerated manifests: `document_existence` **match**, `non_existence` **match**. The
delta's `env.rs` refactor is a strict tightening in every direction — the old ad-hoc parser
defaulted to *dev* on unset, the new `is_production()` defaults to *production*, so
`resolve_ingest_signing_key` now returns `None` (503, no ephemeral key) rather than deriving
one, and the `/zk/prove` `keys_dir` path-override is now off by default. The blanket dev CORS
`http://localhost:*` glob is gone. `OLYMPUS_SIGNED_REQUEST_FRESHNESS_SECS` is clamped and falls
back to 300 s on any parse error.

## Coverage note

**No execution.** Per the read-only rules of engagement, nothing was built, run, or fuzzed. All
findings are static reading plus `git diff`/`git log`, corroborated where feasible by replaying
the exact byte-emission algorithms out of band. Consequences:

- **A1-01's PDF half was reproduced byte-for-byte** (both layouts diffed against the verifier's
  own predicates) and I re-read every cited line at HEAD. **A1-01's OOXML half is traced from the
  vendored `zip-8.6.0` source** (`types.rs:163,351-353,639,692,716`; `datetime.rs:178-198`)
  rather than from an executed `.docx` redaction. One `cargo test` that produces an OOXML
  redaction and hexdumps the central directory would settle it in a minute.
- **L-01's exact overflow threshold is an estimate.** What is proven is that recursion depth
  grows linearly and unboundedly in input length at ~0.67 frames/byte with no cap; the specific
  30–60 KB figure is frame-size reasoning against a 2 MiB Tokio stack. The claim that `abort()`
  orphans the pg-embed child (via skipped `Drop`) is plausible but unverified and is not relied
  on.
- **L-02's memory arithmetic is bandwidth × 30 s reasoning**, not a measured OOM.

**Federation could not be built or tested on this host.** The `federation` cargo feature does not
link on Windows (LNK1181 on `sqlite3.lib` via arti → rusqlite), so that surface is
**read-only-verified**: no two-node exercise, no live Tor path, and specifically no runtime
confirmation of the equivocation semantics or the v3 `.onion` validator's accepting test vector.
The federation hunter noted that a 20-line addition to
`src-tauri/tests/federation_equivocation.rs` running against pg_embed (no Tor needed) would
confirm or refute the detection-scope question that was refuted analytically.

**`pdf-textrun` could not be exercised at all** — `textrun-segmenter` is off by default, so its
823 lines were reviewed statically and it was not confirmed that the module still compiles
against the current `pdf_xref` API. This is the largest single block of new code in the delta
and it carries the Informational verifier gap above.

**Adversarial verification coverage.** 21 candidates were produced across 7 surfaces; **all 21
were put to the 3-skeptic panel and none was dropped unverified** — the workflow log records
zero unverified candidates, so this report contains no "unverified candidates" section. The
